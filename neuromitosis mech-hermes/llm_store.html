0 · thesis

The model store is not a page you visit. It is a module the conductor serves.

Today llm-store.html is a storefront whose omnibox commands are ls models / executeCommand(...) — a CLI in storefront clothing, with no backend: its /api/llm-store/inference fetch cannot resolve on a static host. mech-os.html is the opposite: a rich console (draggable windows, command input, robot canvas, spatial frame, evolving typography) whose telemetry was fabricated until §78 made it measured, and which has no execution behind it.

This specification joins them. This is the estate's own law restated:

one human → many agents needs “us” in between = the conductor (the product).

2 · target architecture

SURFACE   mech-os console (white-labelled)         human looks here
  │       intent in, receipt out — never a key
  ▼
BRIDGE    loopback relay 127.0.0.1:<port>         the only crossing
  │       op → plan → approval → act → receipt
  ▼
CONDUCTOR Hermes (>_h:)                            intent, custody, memory, dispatch
  │       catalogue · policy · fleet waves
  ▼
LEAF      Victus RTX (llama.cpp) · CUDA_MCP² broker → droplet

The bridge is the only boundary. Everything public is static; everything that acts is local. No credential crosses the bridge — only ops and crypto proofs.

5 · the conductor loop

  1. Human types intent in the console.
  2. Console → bridge store.plan.
  3. Conductor resolves catalogue + leaf, writes a plan, stops.
  4. Human approves (explicit). No approval, no act.
  5. Leaf runs; receipt returns through the same bridge.
  6. Console shows plan + receipt side by side. Fan-in: N leaves → one truth.

6 · built for longcat 2.5 ultra max

The build is designed so a long-context, tool-using agent can execute it without holding a wizard's opinion — every stage is specified as a gate the agent can run and prove.

  • long-horizon — the spec is the contract; the agent carries it across sessions and hands off by writing skills, not by re-explaining.
  • tool orchestration — each stage names the exact tool (terminal, read_file, patch, browser_exec, delegate_task) and the exact artifact it produces.
  • parallel fan-out — independent modules (catalogue, pet panel, spatial panel, bridge) are separable and merge behind a PASS gate.
  • self-verification — every stage ends with a command that proves it, and a receipt.
  • procedural memory — each completed stage lands as a skill entry so the next session starts from the mechanism, not the recollection.

Capability is used where it pays: generation, delegation, verification — never as a substitute for a gate.

7 · governance

  • Plan → approval → act. Address is not permission.
  • Motion/spend requires a bound human.
  • Custody never moves. Keys stay on Victus; the page never sees one.
  • Refusal is a result and is logged.
  • One surface, one responsibility: console renders, bridge brokers, conductor decides, leaf runs.

9 · white-label

The console is the product. The white-label layer already proven on the home (glyph, name, accent, persisted locally) extends to the console: the operator wears it, the store keeps its data. Nothing defaults to æ.

10 · verification

One command per stage, plus: the console renders offline; the bridge refuses an unapproved run; a receipt recomputes; the drift sweep stays clean.

11 · blockers, honestly

  • static host — no direct agent call from github.io; the bridge is mandatory, not optional.
  • local inference — local model capability bounds what the leaf can serve; the CUDA_MCP² route is the fallback and is not yet measured end-to-end.
  • catalogue truth — prices are a third-party feed; quote them with source and timestamp, never as our own rates.
  • governance — until stage 3 lands, the console is a viewer. Do not describe it as operable.
